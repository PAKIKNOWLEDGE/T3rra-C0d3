# Taste
- Prefers forking/reusing an existing mature open-source project (and reworking its UI/UX or styling) rather than building a runtime or desktop app from scratch. Confidence: 0.6
- Strongly avoids unstable dependencies/backends that ship frequent breaking changes; treats "research-grade" churn as a dealbreaker and prioritizes stability over novelty when picking a foundation. Confidence: 0.65
- Willing to de-scope/downgrade requirements pragmatically when the original plan proves too costly, rather than pushing the ideal design. Confidence: 0.55
- Wants a research/survey pass over the options before any implementation begins ("先帮我做调研"), deferring the harder design work until the landscape is understood. Confidence: 0.55
- Wants research/analysis results persisted to disk in the current workspace ("落盘") instead of living only in the chat, so the findings become durable project artifacts. Confidence: 0.55
- Strongly likes Hypergryph (鹰角网络, Arknights/Endfield) UI aesthetic — explicitly stated as their favorite style for desktop-app UI work. Confidence: 0.9
- Doesn't want UI styling dogmatically bound to a named style label like "endfield style" — the goal is capturing the authentic feel (对味), not mechanically applying the named style; also wants blind critique of existing work against reference material rather than assuming the current design is right. Confidence: 0.8

- Token-cost conscious: rejects token-expensive processes — explicitly stopped headless browser verification as "非常浪费token" even though the skill's workflow prescribed it; prefer low/zero-token alternatives (reading existing screenshots, handshake-only checks). Confidence: 0.75
- Dark-mode only for UI work: explicitly rejected light themes outright ("亮色直接丢弃，我不想大晚上被闪瞎") — works late at night, bright/light UI is unacceptable as a primary or shipped theme even if a reference style's official identity is light. The accepted ARK standard keeps a dark shell with light selected blocks and a light approval card — light *surfaces* inside a dark shell are accepted. Confidence: 0.9
- Once a design standard is chosen, treats it as the authoritative spec, not loose inspiration — design fidelity is strict. Migrating it must move skeleton, components and copy together; a colours-only port was judged 「不对味」 and to have lost the soul of the standard (2026-09-26). Confidence: 0.85
- Once a direction is decided, prefers jumping straight to a quick static-page demo over further research — "能快速写个demo（就静态页面就行）…还是你要进一步研究" — research is for choosing between options, minimal-scope static prototypes are for judging the result. Confidence: 0.7
- Gated delivery workflow: dependent follow-up work (e.g., persisting docs, writing standards files) must wait for the user's explicit review verdict on the current deliverable before starting — "这得等我审核通过你的交付物后再说". They queue upcoming tasks via casual inline mentions ("这只是随口提一句") and expect the agent to register them without acting early. Confidence: 0.8
- Wants an agent-facing standards doc (AGENTS.md) written as a canonical "standard answer" (标准答案) whenever other agents might take over the work, to keep successor agents from drifting away from the established design/decisions. Confidence: 0.75
- Acceptance bar for deliverables is directional, not perfectionist: judged a static demo by whether it captured the intended feel and approved it as a reference 范本 despite real visual flaws ("虽然错位、字体不全，但是当个范本还可以") — flaws should be recorded as a bounded known-defects list to fix later, not grounds for a rebuild. Confidence: 0.65
